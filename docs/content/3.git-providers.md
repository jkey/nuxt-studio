Git providers handle the synchronization between Studio and your repository. They are responsible for **pushing content changes** (commits) to your Git repository when you publish from Studio.

::note{to="/auth-providers"}
Git providers are distinct from **Auth providers**. Git providers determine where your repository is hosted and enable you to publish content changes, while Auth providers control how users authenticate and gain access to Studio.
::

## Publication Requirements

To publish content changes to your repository, Studio needs a valid access token with write permissions. The token can come from two sources:

### OAuth-based Access (Automatic)

When using **GitHub OAuth** or **GitLab OAuth** as your [Auth provider](/auth-providers), the OAuth token obtained during authentication is automatically used for Git operations. No additional configuration is needed.

```bash [.env]
# GitHub OAuth - token is obtained automatically during login
NUXT_STUDIO_AUTH_GITHUB_CLIENT_ID=<your_github_client_id>
NUXT_STUDIO_AUTH_GITHUB_CLIENT_SECRET=<your_github_client_secret>

# Or GitLab OAuth - token is obtained automatically during login
NUXT_STUDIO_AUTH_GITLAB_APPLICATION_ID=<your_gitlab_application_id>
NUXT_STUDIO_AUTH_GITLAB_APPLICATION_SECRET=<your_gitlab_secret>

# Or Forgejo OAuth - token is obtained automatically during login
NUXT_STUDIO_AUTH_FORGEJO_CLIENT_ID=<your_forgejo_client_id>
NUXT_STUDIO_AUTH_FORGEJO_CLIENT_SECRET=<your_forgejo_client_secret>
```

### Personal Access Token (Manual)

When using **Google OAuth** or **Custom Auth** as your Auth provider, you must provide a Personal Access Token (PAT) with repository write permissions:

```bash [.env]
# For GitHub repositories
NUXT_STUDIO_GIT_GITHUB_TOKEN=<your_github_personal_access_token>

# For GitLab repositories
NUXT_STUDIO_GIT_GITLAB_TOKEN=<your_gitlab_personal_access_token>

# For Forgejo repositories
NUXT_STUDIO_GIT_FORGEJO_TOKEN=<your_forgejo_personal_access_token>
```

::tip
Check the section below to have more info about how to create a PAT for GitHub or GitLab provider.
::

## Automatic Detection

When deploying on **Vercel**, **Netlify**, **GitHub Actions**, or **GitLab CI**, Studio automatically detects the repository `provider`, `owner`, `repo`, and `branch` from the platform's environment variables.

This means you can skip the `studio.repository` configuration entirely on these platforms — just set up your [Auth provider](/auth-providers) and deploy.

::note
Auto-detection applies to all fields, including `branch`. CI-detected values take precedence over manually configured values in `nuxt.config.ts`. To use a specific branch, unset the corresponding CI environment variable (e.g. `GITHUB_REF_NAME`) or configure your deployment platform accordingly.
::

::warning{title="Forgejo/Gitea Actions: provider must be set explicitly"}
For Forgejo and Gitea Actions, the `provider` itself is **never** auto-detected — you must set `provider: 'forgejo'` explicitly in `studio.repository` (or via the auth provider). Only `owner`, `repo`, `branch`, and `instanceUrl` are detected, and only when the `FORGEJO_ACTIONS`/`GITEA_ACTIONS` and `GITHUB_*` environment variables they rely on are present in the **running server process**. On most CI platforms these variables only exist during the build step and are gone once the app is actually deployed and serving requests, so in practice you'll usually need to configure `owner`/`repo`/`branch`/`instanceUrl` manually for Forgejo/Gitea deployments too.
::

::warning
On Vercel, you must enable **[Automatically expose System Environment Variables](https://vercel.com/docs/environment-variables/system-environment-variables#automatically-expose-system-environment-variables)** in your project settings (**Settings → Environment Variables**) for auto-detection to work.
::

## Supported Providers

Studio supports three Git providers for repository operations: GitHub, GitLab, and Forgejo.

### GitHub

When deploying on Vercel or Netlify with a GitHub repository, the configuration below is automatically detected. You can also configure it manually in `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  studio: {
    repository: {
      provider: 'github',
      owner: 'your-username',
      repo: 'your-repo',
      branch: 'main' // Optional, defaults to 'main'
    }
  }
})
```

#### Creating a GitHub Personal Access Token

::warning
This section is required if you're using an [Auth provider](/auth-providers) that doesn't provide Git access (like Google OAuth or Custom Auth). In this case you'll need to create a Personal Access Token to publish your changes.
::

::steps{level="4"}
#### Navigate to GitHub Token Settings

Go to [GitHub Settings → Personal access tokens](https://github.com/settings/personal-access-tokens/new) and create a new **Fine-grained Personal Access Token**.

#### Configure the GitHub Token

Fill in the required fields:

- **Token name**: Your app name
- **Resource owner**: The GitHub organization (or user) the repository belongs to
- **Repository access**: Select **Only select repositories** and choose your repository
- **Permissions**: Click **Add permission** and select **Contents** then update access to **Read and write**

#### Set GitHub Environment Variable

Add the token to your deployment platform's environment variables:

```bash [.env]
NUXT_STUDIO_GIT_GITHUB_TOKEN=<your_github_personal_access_token>
```
::

### GitLab

When deploying on GitLab CI, the configuration below is automatically detected. You can also configure it manually in `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  studio: {
    repository: {
      provider: 'gitlab',
      owner: 'your-username', // or group name
      repo: 'your-repo',
      branch: 'main' // Optional, defaults to 'main'
    }
  }
})
```

::note
**Self hosted GitLab**:

- You can use the `NUXT_STUDIO_AUTH_GITLAB_INSTANCE_URL` to override the default GitLab instance URL if you're using a self-hosted instance.
- [Oauth instance URL](/auth-providers#set-gitlab-environment-variables) is based on the same env variable by default.
::

#### Creating a GitLab Personal Access Token

::warning
This section is required if you're using an [Auth provider](/auth-providers) that doesn't provide Git access (like Google OAuth or Custom Auth). In this case you'll need to create a Personal Access Token to publish your changes.
::

::steps{level="4"}
#### Navigate to GitLab Token Settings

Go to **User Settings → Personal access tokens** (or your group/organization settings if applicable) on GitLab.

#### Configure the GitLab Token

Fill in the required fields:

- **Name**: Your app name
- **Expiration date**: Set according to your security policy (GitLab defaults to 365 days, and non-expiring tokens are not allowed on most instances). See [GitLab's guidance on expiry limits](https://docs.gitlab.com/user/profile/personal_access_tokens/).
- **Scopes**: `api` (required for reading/writing repository content) :warning[Copy the generated token immediately; you won't be able to see it again.]

#### Set GitLab Environment Variable

Add the token to your deployment platform's environment variables:

```bash [.env]
NUXT_STUDIO_GIT_GITLAB_TOKEN=<your_gitlab_personal_access_token>
```
::

### Forgejo

Set `provider: 'forgejo'` explicitly — it is never auto-detected. When running via Forgejo or Gitea Actions, `owner`, `repo`, `branch`, and `instanceUrl` are detected automatically from `GITHUB_*` environment variables, but only if those variables are present in the running server process (usually true only at build time, not after deployment — see the warning above). You can also configure everything manually in `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  studio: {
    repository: {
      provider: 'forgejo',
      owner: 'your-username',
      repo: 'your-repo',
      branch: 'main', // Optional, defaults to 'main'
      instanceUrl: 'https://git.example.com' // Optional, defaults to 'https://codeberg.org'
    }
  }
})
```

::note
**Self hosted Forgejo / Gitea**:

- `repository.instanceUrl` is the primary setting: it's what the browser uses to call the Forgejo/Gitea API directly, and it defaults to `https://codeberg.org`. Set it to your own instance (e.g. `https://git.example.com`) for self-hosted installs.
- This also works with **Gitea ≥ 1.20** — use `provider: 'forgejo'` for Gitea instances too.
- The [OAuth instance URL](/auth-providers#set-forgejo-environment-variables) (`NUXT_STUDIO_AUTH_FORGEJO_INSTANCE_URL`) falls back to `repository.instanceUrl` when it isn't set. Conversely, if only the OAuth instance URL is configured, Studio also uses it for `repository.instanceUrl` — so you only need to set one of the two for a self-hosted instance.
::

::warning{title="CORS is required"}
Studio calls the Forgejo API directly from the browser, so your instance must allow cross-origin requests from your site. Add the following to your instance's `app.ini` and restart Forgejo:

```ini [app.ini]
[cors]
ENABLED = true
ALLOW_DOMAIN = https://your-site.com
METHODS = GET,POST,PUT,DELETE,OPTIONS
HEADERS = Authorization,Content-Type
```

For local development, add `http://localhost:3000` to `ALLOW_DOMAIN` as well (comma-separated).
::

#### Creating a Forgejo Personal Access Token

::warning
This section is required if you're using an [Auth provider](/auth-providers) that doesn't provide Git access (like Google OAuth or Custom Auth). In this case you'll need to create a Personal Access Token to publish your changes.
::

::steps{level="4"}
#### Navigate to Forgejo Token Settings

Go to your Forgejo instance's **Settings → Applications** and generate a new token under **Manage Access Tokens**.

#### Configure the Forgejo Token

Fill in the required fields:

- **Token name**: Your app name
- **Permissions**: Select **repository** with **Read and Write** access

#### Set Forgejo Environment Variable

Add the token to your deployment platform's environment variables:

```bash [.env]
NUXT_STUDIO_GIT_FORGEJO_TOKEN=<your_forgejo_personal_access_token>
```
::

## Working with Branches

By default, Studio commits changes to the branch specified in your configuration (typically `main`). However, you can configure Studio to work with a staging or preview branch instead.

This is useful when you want to review changes on a preview environment before merging to production.

::steps
### Configure Your Branch

Update your `nuxt.config.ts` to target your staging branch.

  :::tip
  Set `NUXT_PUBLIC_STUDIO_REPOSITORY_BRANCH` at deployment time to configure the branch per environment without rebuilding.
  :::

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  studio: {
    repository: {
      owner: 'your-username',
      repo: 'your-repo',
      branch: 'main' // override at runtime via NUXT_PUBLIC_STUDIO_REPOSITORY_BRANCH
    }
  }
})
```

### Deploy Your Staging Environment

Configure your hosting platform to deploy the staging branch to a preview URL (e.g., `staging.yourdomain.com`).

### Configure Auth Provider for Staging

Create a new OAuth App specifically for your staging environment with your staging URL as callback URL. See [Auth Providers](/auth-providers) for setup instructions.

### Set Environment Variables

Configure your staging deployment environment variables depending on the Git and Auth provider you are using.

### Access Studio on Staging

Navigate to `https://staging.yourdomain.com/_studio` to edit content. All commits will be pushed to your configured staging branch.

### Merging to Production

Once you're satisfied with changes on your staging branch, create a pull request from your staging branch to your main branch to deploy to production.
::
